### 2.1 Why the previous session concluded a backup could not be taken here

It could, and the obstacle is arithmetic. The stub loader answers `read_flash`
with one SLIP packet per 4096-byte block and waits for the host's four-byte
acknowledgement before sending the next, so each packet is a USB transfer on its
own:

    4096 + escapes + 2 bytes,   escapes = count(0xC0) + count(0xDB)

A full-speed bulk endpoint carries 64 bytes per packet, and Linux `cdc-acm`
reads in buffers of twice the endpoint size — **128 bytes**. A packet whose
encoded length is 64 more than a multiple of 128 therefore ends with a full
64-byte packet sitting in a half-filled buffer: nothing short arrives to release
it, the device is already waiting for an acknowledgement that needs those bytes,
and esptool times out with `Packet content transfer stopped`. `4098 % 128 == 2`,
so the condition on this host is `escapes % 128 == 62`.

`tools/flash/slip_stall.py` is that predicate, and it was **tested against the
part rather than argued**. Over this 32 MB image it names eleven blocks. All
eleven stall; the two blocks that satisfy the weaker `% 64` condition and not
this one — `0x476000` and `0x5df000` — both read cleanly. Thirteen addresses
tested, thirteen agreeing:

| Block | Escapes | Predicted | Measured |
|---|---|---|---|
| `0x023d000` | 62 | stall | stall |
| `0x0389000` | 62 | stall | stall |
| `0x0476000` | 126 | reads | **reads** |
| `0x04ff000` | 62 | stall | stall |
| `0x0501000` | 62 | stall | stall |
| `0x0533000` | 190 | stall | stall |
| `0x05c6000` | 62 | stall | stall |
| `0x05de000` | 190 | stall | stall |
| `0x05df000` | 126 | reads | **reads** |
| `0x0bef000` | 62 | stall | stall |
| `0x0dcc000` | 62 | stall | stall |
| `0x0dd2000` | 62 | stall | stall |
| `0x0e61000` | 62 | stall | stall |

This resolves the `UNKNOWN` left in
[WAVESHARE_FLASH_LAYOUT](../research/WAVESHARE_FLASH_LAYOUT.md) §2.2, and it
explains why the SLIP-density hypothesis was rejected there on good evidence:
the test used was *rank* — the densest page in a chunk reads fine — and the
condition is a congruence, not a threshold. It also explains why the address
list is partly a fact about the **host**: a host that reads one 64-byte packet
at a time stalls on every multiple of 64, which is the set the Windows and
USB/IP passes recorded, `0x476000` included. Same mechanism, different buffer
size; `slip_stall.py --host-read 64` prints that set.

`tools/flash/backup_flash.py` now changes *method* on failure — the stub first,
the ROM loader after — instead of retrying a deterministic failure. The whole
32 MB read in one run of about 20 minutes.

## 3. The RAM route, and the three faults it found

```sh
idf.py -B build-ram -DSDKCONFIG=build-ram/sdkconfig \
       -DSDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.ramprobe" build
python3 tools/flash/ramhold.py firmware/build-ram/attadipa.bin 30
```

Three things were wrong before this produced a boot, and none of them would have
been found by building:

1. **`sdkconfig.ramprobe` never produced a RAM image.**
   `CONFIG_APP_BUILD_TYPE_PURE_RAM_APP` is a sub-option of the RAM build type
   (`depends on APP_BUILD_TYPE_RAM`), so setting it alone is dropped in silence:
   the generated config came back with `CONFIG_APP_BUILD_TYPE_APP_2NDBOOT=y` and
   the build reported success. Both symbols are set now.
2. **`CONFIG_ESPTOOLPY_FLASHSIZE` does not exist in a pure-RAM build**, so the
   flash-id line was a compile error rather than a wrong value.
3. **`esp_partition_find()` panics in a pure-RAM image.** It reaches
   `spi_flash_mmap`, whose callbacks are only registered with the flash driver:
   `assert failed: spi_flash_mmap spi_flash_mmap.c:200`. The firmware printed
   every line above it and then rebooted. The code had assumed an empty
   iterator; "no partition table to read" and "no flash driver to ask" are
   different states.

**What the RAM route cannot show, and it is most of the acceptance list:** the
flash JEDEC id, PSRAM presence and mode, and the partition table. A pure-RAM
image leaves Cache, MMU, Flash and PSRAM uninitialised by definition. It proves
the SoC, the reset reason, the heap, and that `platform/` links and answers.

- `Board      : Waveshare ESP32-S3-Touch-AMOLED-2.06 (waveshare-amoled-206),

**`Reset : unknown (ESP-IDF code 11)` is correct and will keep appearing.** Code
11 is `ESP_RST_USB`: a host opening or closing the port drove it. The firmware
maps it to `Unknown` on purpose rather than to `ExternalPin`, so that a
developer's cable is never logged as a hardware fault.

## 5. What is not proven here

- **Nothing about the T-Watch.** It is not in hand.
- **No display, no touch, no PMU, no RTC, no radio.** There is no driver in this
  firmware; that is T-166 and beyond.
- **Nothing about power.** No current was measured in this session.
- **Longevity:** the longest continuous run observed was 30 seconds on the RAM
  route and about 12 seconds from flash. "Runs indefinitely" would be an
  estimate wearing a measurement's clothes.

## 6. Bench state after acceptance

Later on 2026-08-25 the T-165 image left the panel bright while providing no
touch or display control, which is expected from §5 but unsafe as an idle bench
state. At the owner's request the complete factory backup from §2 was restored
to the same stable USB identity, `28:84:85:B2:18:A4`.

Before writing, the host rechecked the asset as 33 554 432 bytes with SHA-256
`c423dad3f0d33d56fa96f8590b3da583b05584e85bc2701a7c48c031ad747dbd`, and
`esptool flash_id` confirmed the target MAC, 32 MB JEDEC `c8 40 19` flash and
8 MB PSRAM. The full write ended with:

```text
Wrote 33554432 bytes (6931366 compressed) at 0x00000000 in 157.7 seconds
Hash of data verified.
Hard resetting via RTS pin...
```

A separate full post-restore `verify_flash` was started and then interrupted at
the owner's request because it was redundant for restoring screen control. It
produced no verdict and is **not** claimed as completed; the write's integrated
hash check above did complete, while §2 remains the prior full-device
verification of the backup source.

After the reset the owner directly observed the factory UI at high brightness,
working touch, and then set brightness to minimum. That safe factory state was
later replaced by the reversible T-166 probe below. It remains evidence that
the panel and touch hardware worked before the Attadipa driver run.
